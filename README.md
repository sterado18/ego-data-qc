# ego-data-qc

頭に付けたカメラで家事を撮影し、ロボット学習（模倣学習）に使える品質かを自動で判定する小さな検証。
一人称映像の検品（合否と理由の付与）、S3 転送の完全性確認、学習済みモデルの推論記録までを一人で一周した。

## 結果

### 撮影の改善（同じ15エピソードで比較）

第1ラウンドの不合格の主因は「手が画面の端から外れる」だった。第2ラウンドでは**カメラを少し下に向け、手元を画面中央に入れる**1点だけを変えて撮り直した。

| タスク | 第1ラウンド | 第2ラウンド |
| --- | --- | --- |
| A：コップを水切りかごに置く | 3/5 | 4/5 |
| B：床でタオルをたたむ | 0/5 | 4/5 |
| C：冷蔵庫から取り出して扉を閉める | 5/5 | 5/5 |
| 計 | 8/15 | **13/15** |

床の作業（B）では、手が写るコマの平均が 71% → 99%、両手が写るコマが 5〜13% → 81〜86% になった。

### 第1ラウンド全体（30本）

- 合格 20本／不合格 10本（不合格率 33%）。理由は手の映り不足 6、両手の映り不足 4、ブレ（目視）2（重複あり）
- タスク別の合格：A 8/12、B 4/10、C 8/8
- わざと失敗させた3本のうち1本は、品質基準を満たしたため「失敗例」としてラベル付きで採用

### 指標の検証：ブレは自動で落とさず「要目視」にした

当初はブレたコマ（鮮明さ＝ラプラシアン分散 < 30）が20%を超えたら不合格にしていた。第2ラウンドで画角を下げると不合格が急増したため、人の目で正解ラベルを付けた20コマと照合した。

- 旧判定と人の目の一致は **4/18**（判断保留の2コマを除く）。旧判定が「ブレ」とした14コマのうち、人が見てブレていたのは0コマ
- 原因：ラプラシアン分散は輪郭の量なので、無地の床や黒い袖が画面を占めるとブレていなくても低く出る
- 手の周りだけで測る案、動画内の最良コマとの比で測る案も試したが、どちらも人の判定を分けられなかった
- そこでブレは合否に使わず、超えた動画に「要目視」の印を付けて人が判定する形にした。要目視16本のうち、人が不合格としたのは3本（いずれも床の作業で頭が動いた瞬間）

### 再現性（Ubuntu）

- Multipass の Ubuntu 24.04（arm64）で `setup.sh` → `score.py` を実行し、パイロット5本の合否が Mac と一致
- 数値は小数点以下でずれた（手の映り率で最大 +0.012）。ライブラリの版をそろえても残るため、OS 差と判断
- 再現に必要だった固定：apt の依存（`libegl1` `libgles2`）、ライブラリの版（`requirements.txt`）、Python 本体（`.python-version` で 3.12.10）

### S3 転送の完全性確認

合格した動画を S3 に送り、取り直して照合（`verify_upload.sh`）。

```text
件数 3 → 3 / 容量 75960KB → 75960KB / 指紋（sha256） OK
```

### 学習済みモデルの推論（PushT）

`lerobot/diffusion_pusht`（LeRobot 0.6.1、Mac mps）で10回評価し、**6/10 成功**。失敗4回も最高到達度は 0.96〜0.99 で、「T の縦棒だけ目標からずれる」「押し過ぎて通り越す」という最後の詰めでの失敗だった。詳細と、動かすまでに回避した4つの問題（LeRobot の変換ツールのバグを含む）は [experiments/log.md](experiments/log.md)。

## 判定基準（scripts/score.py）

| 項目 | 基準 |
| --- | --- |
| 手の写り率 | 手が写るコマが 70% 以上 |
| 両手の写り率 | 50% 以上（タオルを畳むタスクのみ） |
| ブレ | 合否に使わない。ブレたコマが 20% を超えたら「要目視」 |
| 照明 | 暗すぎ・明るすぎのコマが 10% 以下 |
| 長さ | 5秒以上、タスクごとの上限の2倍以内 |
| 人の判定 | metadata.csv の `self_flag` に理由があれば不合格 |

## 使い方

```bash
bash setup.sh                                               # 環境づくり（Ubuntu / macOS）
.venv/bin/python scripts/score.py --out reports/scores.csv  # data/raw の動画を採点し、合格分を data/accepted へ
BUCKET=... bash verify_upload.sh                            # 合格分を S3 に送り、件数・容量・チェックサムで照合
```

動画は公開していない（`data/raw/` は .gitignore 済み）。別の場所の動画を使うときは `EGO_RAW_DIR=/path/to/videos` か `--raw` を指定する。
撮影の段取りは [notes/shooting.md](notes/shooting.md)、採点の流れは [notes/pipeline.md](notes/pipeline.md)、来歴は [data/metadata.csv](data/metadata.csv)。

## 限界

- 撮影者は1人、場所は自宅1か所、1ラウンド15〜30本と小さい
- 第2ラウンドの A は動作がやや遅く（平均で約2秒長い）、画角の効果と動作速度の効果を分けられていない
- 第2ラウンドは第1ラウンドの直後（約15〜25分後）に撮影しており、窓の光の変化は部屋の照明で抑えたが完全には揃っていない
- 指標の検証に使った正解ラベルは20コマで、人がブレと判定した例は1コマだけ

## 分からなかったこと

1. **ブレを自動で正しく測る方法**。輪郭の量を使う指標（全体・手の周り・動画内の比）はどれも場面の模様に左右され、人の判定を分けられなかった。カメラの動き（オプティカルフローやスマートフォンの IMU）で測れば場面に依存しないと考えているが、未検証。
2. **Mac と Ubuntu で数値が小数点以下でずれる原因**。ライブラリの版をそろえても残る。動画のデコードか、MediaPipe の計算経路の違いと見ているが、切り分けていない。基準ぎりぎりの動画では OS によって合否が割れうる。
3. **PushT の失敗が最後の詰めで起きる理由**。位置はほぼ合うが、角度の微調整ができない回と、押し過ぎる回があった。方策そのものの限界か、評価の打ち切り時間（300ステップ）との関係かを切り分けていない。
